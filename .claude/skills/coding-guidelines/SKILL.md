# Coding Guidelines

通用開發行為準則，降低常見 LLM coding 錯誤。寫程式、改程式、重構前適用。
**取捨**：這些準則偏向謹慎而非速度；瑣碎任務可自行斟酌。

## 1. 先釐清，再動手

**不要假設。不要藏起困惑。把取捨攤開。**

- 明講你的假設；不確定就問，不要默默選一個。
- 有多種解讀 → 全部攤開，讓使用者選，不要自己挑。
- 有更簡單的解法 → 主動說，必要時 push back。
- 有看不懂的地方 → 停下，指出哪裡不清楚，發問。

## 2. 最小實作

**只寫解決問題需要的程式碼，不做任何臆測性的東西。**

- 不做沒被要求的功能。
- 單次使用的程式碼不抽象化。
- 不加沒被要求的「彈性」或「可設定性」。
- 不為不可能發生的情況寫錯誤處理。
- 200 行能寫成 50 就重寫。

自問：「資深工程師會不會覺得這過度複雜？」會 → 簡化。

## 3. 外科手術式修改

**只動非動不可的部分；只清自己造成的爛攤子。**

- 不順手「改善」鄰近的程式碼、註解、排版。
- 不重構沒壞的東西。
- 配合既有風格，即使你會用不同寫法——先看現有實作再下手，保持一致。
- 重構時保留所有現有行為；穩定後才移除多餘邏輯。
- 看到無關的 dead code → 回報，不要刪。
- 只清掉自己改動造成的孤兒（unused import / 變數 / 函式）；既有 dead code 不主動刪。

檢驗：每一行改動都能直接追溯到使用者的需求。

## 4. 目標驅動

**先定義成功標準，再 loop 到驗證通過。**

把任務轉成可驗證的目標：
- 「加驗證」→「先寫 invalid input 的測試，再讓它通過」
- 「修 bug」→「先寫一個重現它的測試，再讓它通過」
- 「重構 X」→「確保前後測試都通過」

多步驟任務先列簡短計畫：
```
1. [步驟] → 驗證：[檢查]
2. [步驟] → 驗證：[檢查]
3. [步驟] → 驗證：[檢查]
```

強的成功標準能讓你自己 loop 到完成；弱標準（「能動就好」）會需要一直回頭確認。

## 5. 溝通

用最直白的方式解釋：說「防止什麼事發生」，不要說「在做什麼操作」。
